# Application: net_serial_bridge

Remote a UART stream over TCP. Bytes received on one serial port go to a TCP
client, and bytes from that client go out the serial port. Raw bytes, no
framing, one client at a time.

Generated by `app_gen` from `common/templates/app`, then extended by hand. The
answers are recorded in `.copier-answers.yml`; `app_gen update
net_serial_bridge` re-applies template improvements on top of local edits.

| | |

## Building

```bash
make BOARD=w55rp20_evb_pico PRISTINE=y build                                   # bridge uart0
make BOARD=w55rp20_evb_pico PRISTINE=y CMAKE_OPTS="-DAPP_SERIAL_SRC=cdc_acm" build
make flash
```

`APP_SERIAL_SRC` is a CMake cache variable, so switching it needs
`PRISTINE=y`. Boards need their fully qualified target on Zephyr 4.0.
`make help` lists every target.

## Serial source

`SerialPipe` binds to the devicetree chosen node `zephyr,uart-pipe`, so the
bridged port is a build-time choice. `CMakeLists.txt` maps `APP_SERIAL_SRC` to
one conf fragment plus one overlay, and verifies after Kconfig runs that the
mirrored `choice APP_SERIAL_SRC` agrees.

| `APP_SERIAL_SRC`  | Bridged port                | Console            | Files                                                  |
|-------------------|-----------------------------|--------------------|--------------------------------------------------------|
| `uart0` (default) | uart0, GP0 (TX) / GP1 (RX)  | USB CDC-ACM        | `conf/serial_uart0.conf`, `boards/serial_uart0.overlay`   |
| `cdc_acm`         | USB CDC-ACM (USB-C)         | uart0, GP0 / GP1   | `conf/serial_cdc_acm.conf`, `boards/serial_cdc_acm.overlay` |

On the development bench the Raspberry Pi Debug Probe's UART is on GP0/GP1 and
the board's USB-C is on the host, so the two modes swap which `/dev` node is
the bridge and which is the console:

| Device                                                        | `uart0` mode | `cdc_acm` mode |
|---------------------------------------------------------------|--------------|----------------|
| `/dev/serial/by-id/usb-Raspberry_Pi_Debug_Probe__CMSIS-DAP__*-if01` | bridge       | console        |
| `/dev/serial/by-id/usb-ZEPHYR_USB-DEV_*-if00`                 | console      | bridge         |

Do not combine `SNIPPET=probe-console` with `uart0` mode: console output would
interleave into the bridged stream.

The UART runs at 115200 (board devicetree). CDC-ACM has no baud rate and no
flow control toward the host, so `conf/serial_cdc_acm.conf` enlarges the
receive buffers. A host that streams without pause still loses data; pace
bulk transfers from the host side. CDC-ACM also discards TCP->serial bytes
while no host program has the port open.

## Bridge design

Two threads and one `k_fifo`:

- `src/bridge_serial.c`: a thread polls `SerialPipe_rxGet()` every
  `CONFIG_APP_BRIDGE_SERIAL_POLL_MS`, packs bytes into 256-byte items from a
  static slab, and queues an item when it is full or when one poll period
  passes with no new bytes. When the pool is empty it drops the oldest queued
  item, so a client that connects later sees the most recent serial output.
- `src/bridge_tcp.c`: `TcpServer` with a receive poll timeout
  (`CONFIG_APP_BRIDGE_TCP_POLL_MS`). Its callback forwards socket bytes to
  `SerialPipe_send()`, waiting up to `CONFIG_APP_BRIDGE_TX_WAIT_MS` for
  transmit pool space (this closes the TCP window while the UART drains), then
  drains the fifo to the socket.

Queued serial bytes survive a client disconnect and go to the next client.

| Kconfig                            | Default | Meaning                                       |
|------------------------------------|---------|-----------------------------------------------|
| `APP_BRIDGE_TCP_PORT`              | 12001   | Listen port                                   |
| `APP_BRIDGE_ITEM_SIZE`             | 256     | Bytes per queue item                          |
| `APP_BRIDGE_POOL_DEPTH`            | 16 (64 for cdc_acm) | Items in the slab                 |
| `APP_BRIDGE_SERIAL_POLL_MS`        | 2       | Serial poll period and idle flush gap         |
| `APP_BRIDGE_TCP_POLL_MS`           | 10      | TcpServer poll timeout                        |
| `APP_BRIDGE_TX_WAIT_MS`            | 250     | Max wait for SerialPipe transmit pool space   |
| `APP_BRIDGE_SERIAL_STACK_SIZE`     | 1024    |                                               |
| `APP_BRIDGE_SERIAL_THREAD_PRIO`    | 9       |                                               |
| `APP_BRIDGE_TCP_STACK_SIZE`        | 4096    |                                               |
| `APP_BRIDGE_TCP_THREAD_PRIO`       | 10      |                                               |

Thread stacks for both TcpServers and the RPC buffers come from
`CONFIG_HEAP_MEM_POOL_SIZE` (`conf/kernel.conf`).

## Testing

`test/bridge_test.py` drives both ports at once. It needs only the standard
library.

```bash
# uart0 mode: bridge on the probe UART
../../python/.venv/bin/python test/bridge_test.py

# cdc_acm mode: bridge on the board's USB-C
../../python/.venv/bin/python test/bridge_test.py \
    --serial /dev/serial/by-id/usb-ZEPHYR_USB-DEV_554D383836380019-if00 \
    --pool-bytes 16384
```

It checks serial->TCP, TCP->serial, both at once, bytes held while no client
is connected, drop-oldest on a burst of twice the pool, and reconnect. Quick
manual check:

```bash
nc 192.168.1.15 12001            # then type into minicom on the bridged port
```

### View with minicom

`scripts/bridge_minicom.sh [ip] [port]` presents the TCP stream as a
pseudo-terminal with `socat` and opens it in minicom (colour on, hardware flow
control off through a `~/.minirc.netbridge` profile it creates on first run).
Ctrl-A X exits. When the connection drops the script closes minicom and
reports it; run it again to reconnect.

## Networking

Wired ethernet via the board's MAC/PHY. The interface comes up through Zephyr's
connection manager; see `src/net_l4.c`. Addressing is static, applied by
`src/net_ip.c` from `conf/ip.conf`.

The transport is declared **per board** in `boards/<board>.conf` as
`CONFIG_APP_NET_TYPE_<X>=y`, so one application can use different transports on
different boards. `common/scripts/cmake/app_net_type.cmake` reads that
declaration before Kconfig runs and asserts afterwards that the two agree.

## RPC

A ProtoRpc server listens on TCP port `CONFIG_TCPRPCSERVER_PORT` (default 13001)
with COBS framing. `SystemRpc` and `RtosUtils` callsets are registered in
`src/rpc.c`; add more there. Callsets are discovered by the host at runtime, so
there is no `callsets.yaml` to maintain. `proto/app.proto` defines an app
callset that is compiled but not yet registered.

```bash
rtosutils-cli --ip 192.168.1.15 get-tasks
```

Build the host-side protobuf bindings with `make proto`.

## LED

`src/led.h` exposes `app_led_init()`, `app_led_set()` and `app_led_toggle()`,
driving the devicetree `led0` alias the way `applications/blinky` does.

## Layout

```
CMakeLists.txt   conditional sources, conf/ fragment and overlay selection
Kconfig          APP_NET_TYPE, APP_SERIAL_SRC and bridge options
prj.conf         app-wide defaults
conf/            one fragment per concern; ip.conf owns addressing
boards/          board .conf/.overlay plus the two serial-source overlays
src/             main.c plus one file per subsystem (see src/app.h)
test/            host-side end-to-end test
```

`src/app.h` defines the init contract: every subsystem provides an
`app_*_init()`, and a no-op inline stands in when it is not built, so `main.c`
contains no preprocessor logic.
